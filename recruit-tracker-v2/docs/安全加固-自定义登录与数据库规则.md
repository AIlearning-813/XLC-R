# 安全整改：自定义登录 + 数据库规则收紧

> 起因：2026-09-30 实测发现生产库对匿名访客**可读且可写**
> （12/12 集合可读、16/16 写操作放行），详见下文证据。

## 一、问题与证据

用仓库自带探针（与外部访客完全相同的能力：匿名登录 + 前端同款 SDK）实测线上环境
`xlc-recruit-d1gmbx8gybc8a3565`：

```bash
node scripts/probe-anon-access.cjs   # 匿名可读集合数：12，被正确拒绝：0
node scripts/probe-anon-write.cjs    # 有 16 个写操作被放行
```

暴露内容包含 `Candidate` 的姓名/手机号/邮箱/`resumeRawText`，以及 `EmailConfig`
的 `imapHost`/`imapUser`/`imapPassword` 字段；写权限还可篡改 `ownerId`、删除数据、
清空 `AuditLog`。

环境 ID 打包在公开前端产物中，**任何知道站点域名的人都能复现**。

## 二、根因

前端用 CloudBase **匿名登录**获取 SDK 上下文（`useAuthStore.initSDK`），
真正的身份验证走 `auth-proxy` 云函数，但校验结果没有传给 CloudBase 会话。
数据库安全规则只能看到 `auth.uid`（随机匿名 ID），而业务归属 `ownerId` 是
「王莉」这类用户名，`doc.ownerId == auth.uid` 永不成立 —— 规则因此形同虚设。

## 三、改造顺序（关键：不需要停机）

| 步骤 | 动作 | 系统状态 |
|---|---|---|
| ① | 部署前端 + `auth-proxy`（自定义登录票据，失败自动回退匿名） | 正常，用户无感 |
| ② | 验证登录、读写均正常 | 正常 |
| ③ | 收紧数据库规则为「仅登录用户可读写」 | 瞬时切换；已登录用户无感，匿名访客立即被挡 |

**不要把顺序颠倒**：先收紧规则会导致前端所有直连读写被拒，系统停用。

## 四、控制台配置（一次性）

1. 腾讯云开发控制台 → 环境 `xlc-recruit-d1gmbx8gybc8a3565` → **登录授权** → 开启**自定义登录**
2. 生成密钥对，**私钥配置到 `auth-proxy` 云函数的环境变量**（切勿使用
   `tcb config update fn --overwrite`，会覆盖已有的 `MASTER_SECRET` 等变量）
3. 未完成上述配置前，`createTicket` 会失败；代码已做容错，
   `issueCustomTicket` 返回 null，登录照常走匿名会话（即改造前行为）

## 五、要应用的数据库规则

对下列集合，将读写规则设为「仅登录用户」：

```json
{ "read": "auth.uid != null", "write": "auth.uid != null" }
```

适用集合：`Candidate`、`Application`、`Job`、`RecruitmentDemand`、`Config`、
`KnowledgeBase`、`CompanyProfile`、`EmailConfig`、`PendingChanges`、
`RecruitmentInsight`、`ParseNotification`、`CommunicationLog`、`DuplicateExclusion`、
`ParseCorrectionBank`、`ReportCache`、`LoginLog`、`AuditLog`

**`Users` 集合应设为完全禁止客户端访问**（含 `passwordHash`/`salt`，只允许云函数经特权访问）：

```json
{ "read": false, "write": false }
```

> 注意：仓库中旧的 `scripts/set-security-rules.cjs` 写错了集合名（`User` 单数，
> 而代码使用 `Users` 复数），且规则基于 `doc.ownerId == auth.uid` 的假设不成立，
> 不可直接使用。

## 八、脚本化执行（推荐，替代控制台逐个点选）

控制台逐集合设置权限既慢又无法留痕。已提供脚本 `scripts/apply-db-security-rules.cjs`：

```bash
# 0) 准备（只需一次）。避免为一个运维脚本给项目增加 300+ 依赖，放临时目录即可：
mkdir /tmp/cbsdk && cd /tmp/cbsdk && npm i @cloudbase/manager-node
export CBSDK_DIR=/tmp/cbsdk

# 1) 凭据只放本机环境变量，不要写进文件、不要提交
export TENCENTCLOUD_SECRETID=<SecretId>
export TENCENTCLOUD_SECRETKEY=<SecretKey>

# 2) 先看当前状态（只读）
node scripts/apply-db-security-rules.cjs --status

# 3) 确认自定义登录已切换、并已验证登录与读写正常之后，再收紧
node scripts/apply-db-security-rules.cjs --apply --yes

# 4) 验证：期望两个探针都报告 0
node scripts/probe-anon-access.cjs
node scripts/probe-anon-write.cjs

# 紧急回滚（会重新暴露漏洞，仅供故障恢复）
node scripts/apply-db-security-rules.cjs --rollback --yes
```

脚本基于腾讯云 `ModifyResourcePermission` 接口（经 `@cloudbase/manager-node` 的
`permission` 服务）：`Users` 设为 `ADMINONLY`，其余 17 个集合设为 `CUSTOM` +
`{"read":"auth.uid != null","write":"auth.uid != null"}`。
若环境启用的是 OPA 授权引擎，脚本会先行提示需要改用 `modifyEnvAuthzConfig`。
## 九、部署加固代码的前置条件（务必先读，否则会导致功能不可用）

部署后会「失败关闭」——所有调用被拒、功能整体不可用。**

| 函数 | 现有环境变量 | 部署加固代码前是否需要先补配置 |
|---|---|---|
| `get-file-url` | （无） | ❌ 必须先配置 `MASTER_SECRET` |
| `report-aggregator` | （无） | ❌ 必须先配置 `MASTER_SECRET` |
| `rag-assistant-proxy` | `DEEPSEEK_API_KEY` | ❌ 必须先配置 `MASTER_SECRET` |
| `email-scanner` | `MASTER_SECRET`、`SALT_PEPPER`、`TENCENT_SECRET_ID/KEY` | ✅ 可直接部署 |

否则令牌签得出、验不过（令牌由 auth-proxy 签发，由各函数校验）。

### 部署操作要点（已实测）

- 用 `tcb fn code update <name> --dir . --deployMode zip`（**只改代码**，不动环境变量）
- **CWD 必须是函数目录**，`--dir` 必须是相对路径 `.`；
  传绝对路径且 CWD 不在该目录时，CLI 会打出**空 zip**，平台报
  `InvalidParameter.ZipCodeFmt: zipfile is empty`，而 CLI 仍打印「更新成功」
- CLI 的「更新成功」提示不可信，**必须**用 `tcb fn detail <name> --json` 复核
  `Status`（应为 `Active`）与 `StatusReasons`（应为空）
- **绝不要**用 `tcb config update fn ... --overwrite`，它会抹掉已有环境变量
- 回滚：把改动前的代码目录重新 `code update` 上去即可（本次事故即用此方式恢复）
### 部署前必须先跑前置检查

```bash
node scripts/preflight-fn-deploy.cjs        # 或 npm run preflight:fn
```

脚本会扫描仓库中引用了 `MASTER_SECRET` 的函数，逐个比对线上是否已配置；
**有缺失即以退出码 1 结束**，可直接放在部署命令前面作为门禁。
它只读取变量名，不打印任何值（拉取用的临时文件读后即删）。

### 清单完备性由脚本自检（2026-09-30 增设）

`apply-db-security-rules.cjs` 会**扫描前端源码**（`src/**` 中字面量形式的
`.collection('X')`），与保护清单比对：

- 有遗漏 → 打印「保护清单不完整，缺少：…」并**中止 --apply**（退出码 1）
- 齐全 → 打印「✔ 保护清单完备」

**由来**：初版清单漏了 `ErrorLog`（`src/services/error-capture.js` 直连写入），
若照此执行，该集合会继续对匿名访客敞开读写——又是一个「看起来修好了」的缺口。
自检可防这类遗漏再次发生。

另经核对：**前端没有任何直连 `Users` 的调用**，故 `Users` 设为 `ADMINONLY`
（客户端完全禁止）是安全的；它含 `passwordHash`/`salt`，必须只由云函数特权访问。

> 提示：`ReportCache`、`LoginLog` 前端也不直接访问，理论上可进一步收紧为
> `ADMINONLY`。为降低误伤风险，当前仍按「仅登录用户」处理。
### 收窄后的边界（重要：勿误以为「已完全安全」）

方案 A 关闭的是**匿名访客**通道。规则的粒度是「是否登录」，**不是角色**：

- 任一已登录用户仍可直连读写 `EmailConfig`（含 `imapPassword` 字段）、`AuditLog` 等
- 这些集合前端确有直连调用（如 `services/handover.js` 读 `EmailConfig`、
  `views/CandidateDetailPage.vue` 读 `AuditLog`），因此无法直接设为 `ADMINONLY`
  （唯一确认无前端直连的是 `Users`，已设为 `ADMINONLY`）

要按角色细分，必须把这些敏感读取迁到云函数、走 `_shared/access-guard.js`
（即此前评估过的「方案 B」）。在此之前请知晓：
**匿名通道已关，但租户内的横向权限尚未收敛。**

### 切换时的存量会话（已在代码中处理）

自定义登录上线后，存量用户的 CloudBase 会话仍是**匿名**的（本地却存有登录态）。
规则收紧后这类会话会被拒，界面会表现为「已登录却到处报错」，极难排查。

`useAuthStore` 已加入**会话一致性守卫**：当检测到「本地存有登录态 + SDK 会话为匿名」
时，主动清除本地登录态并要求重新登录，日志给出明确原因。
失败方向是安全的——万一判断有误，最多让用户多登录一次，不会损坏数据。
判据取自官方文档：`loginState.isAnonymousAuth`。

### 更正：`db-backup` 的「备份清理」修复实际无效（2026-09-30 复核）

前文建议「评审后部署」`db-backup` 的仓库版本。**复核后发现该实现调用了不存在的 API**：

```js
await app.listDirectoryFiles({ prefix: 'backups/' });
```

而当前函数内安装的 `@cloudbase/node-sdk` 只提供 `deleteFile` / `getTempFileURL`，
**没有 `listDirectoryFiles`**（已在其类型定义中核实）。因此该段逻辑必然抛错，
被外层 `try/catch` 吞掉——**部署上去也不会真正清理旧备份**，与线上现状无异。

结论：`db-backup` 暂不需要部署；若确实要清理旧备份，应改用当前 SDK 支持的接口
（例如按已知路径前缀拼出文件 ID 后用 `deleteFile`），或按原注释所说在
CloudBase 控制台配置**存储生命周期策略**（更省事、无代码风险）。

这也说明：**「仓库版本更新」不等于「修复有效」**——部署前必须确认所调用的 API
在当前运行环境中确实存在。

## 十二、云函数级暴露面（2026-09-30 实测 + 代码检查）

### 结论一：匿名访客可直接调用云函数（实测）

用与前端相同的 SDK + 匿名登录（等同外部访客能力）调用只读函数 `get-storage-usage`：

```
✔ 匿名登录成功（与外部访客同等能力）
⚠️ get-storage-usage —— 匿名调用【成功】
   返回: {"ok":true,"totalFiles":0,"totalSize":0,"quotaBytes":3221225472,...}
```

即：**云函数调用通道对匿名用户开放**。系统本身依赖它完成登录
（`auth-proxy` 必须匿名可调用），因此**不能整体关闭**，只能逐函数收紧。

### 结论二：19 个函数中 14 个没有任何身份校验（代码静态检查）

| 分类 | 数量 | 函数 |
|---|---|---|
| 有身份校验 | 5 | `auth-proxy`、`email-scanner`、`get-file-url`、`parse-queue-processor`、`report-aggregator` |
| 无校验 + **可删除数据** | 3 | `cleanup-test-data`、`db-backup`、`report-cache-warmer` |
| 无校验 + 可写入数据 | 11 | `archive-old-applications`、`db-diagnose`、`fix-missing-jobs`、`get-storage-usage`、`health-monitor`、`history-insight-generator`、`init-department-tree`、`rag-assistant-proxy`、`resume-parser-proxy`、`web-search-agent`、`write-audit-log` |
| 无校验 + 线上孤儿 | 1 | `refetch-resumes` |

> ⚠️ **方法的边界（务必如实理解）**：调用通道开放是**实测**的；
> 「14 个函数无身份校验」是**代码静态检查**得出的。
> 为避免造成真实副作用，我**故意没有**去调用其中的删/写函数。
> 故上表是「通道开放 + 无校验 ⇒ 可达」的**推断**，不是逐个实测的结果。

### 修复路径与各自的卡点

1. **云函数级安全规则（最优）**：CloudBase 支持按函数设权限——`@cloudbase/manager-node`
   的 `permission.modifyResourcePermission`，`resourceType: 'function'`（合法值仅 `CUSTOM`）。
   **卡点：需要腾讯云凭据。**
   注意规则须**逐函数**设置：`auth-proxy` 必须保持匿名可调用，否则无人能登录。
2. **函数内加守卫**（复用 `_shared/access-guard.js`）：**卡点：需要 `MASTER_SECRET`**，
   而这些函数目前均未配置该变量（与 `get-file-url` 同款前置条件）。
3. **删除一次性函数（最省事）**：`cloudbaserc.json` 注释显示 `init-department-tree`
   等为「一次性云函数」；`cleanup-test-data`、`db-diagnose` 本就不在线上。
   若确认已无用，删除即彻底消除风险。
4. **控制台手动收紧（你可立即做）**：云开发控制台 → 云函数 → 目标函数 → 权限设置。

### 优先收紧对象：定时器专用函数

`db-backup`、`health-monitor`、`parse-queue-processor`、`email-scanner`、
`report-cache-warmer`、`archive-old-applications` —— 这些只需定时触发，
客户端调用毫无必要，应优先限制为「仅管理端/定时触发」。

> ⚠️ 不能用「event 里是否带 Timer 标记」来判断调用来源：客户端通过
> `callFunction` 传入的 `data` 会成为事件对象，该字段可被伪造，不构成访问控制。
